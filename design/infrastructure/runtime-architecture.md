# 运行时与性能架构

## 0.2.4 建设驱动股票迁移

V22保留历史股价、交易、持仓、建设度和原EMA，只修正当前繁荣度，为每日快照增加公式版本，增加行业幅度EMA。旧快照由股票追赶换算读取，原快照不重写。旧末名连续天数归零，已有退市和冷却日期保留。

黑天鹅保存第二玩家、规则版本、第二玩家基线和第二股票目标。升级前在途事件按旧规则完成，新事件用两人四行业规则。群组服统一升级，主服执行迁移。尺度、股价和事件应用同一事务，回滚及重试不重复吸收幅度、不重选目标。

## 0.2.3 热路径与汇总优化

股票筛选排序结果属于单个不可变Dashboard快照，按规范化搜索、排序、持仓过滤和行业集合缓存；新快照创建新缓存，窗口重建仍读取当前筛选条件。持仓列表在同一快照内缓存。变化时仍执行原筛选和排序，未变化时不扫描股票或排序，服务端交易权限不在缓存中判断。

方块去重采用有界LinkedHashMap的最近访问顺序，重复访问移至末尾且刷新20tick窗口；每20tick仅迭代到期前缀，遇到未到期项立即停止。空间仍按不同键增长，上限50000，满额新键仍拒绝，已存在键可刷新；原始放置/挖掘统计与行业去重资格分离。整数tick回绕、到期边界及刷新顺序有专项检查，无世界扫描。

总建设度排行新增V21表player_development_total，DECIMAL(30,0)精确存储九内置行业之和，迁移一次性回填旧统计，不修改旧迁移或删除原表。统计批次仅对涉及玩家按UUID排序锁定总计行，写行业增量后，在同事务内以每玩家最多九个源行重算该玩家汇总；不依赖内存增量或按long截断总和。读取排行榜使用汇总索引，不再对全体行业明细GROUP BY；缓存15秒、top100、机器人排除、UUID同值排序不变。UUID迁移和机器人清理包含新表，批次重放与事务回滚不改变总计。共享数据库节点应统一升级，不能继续用旧节点写统计；旧世界由Flyway自动迁移，升级前备份数据库，不直接降级至旧版。

时钟广播在服务端线程中对支持通道的玩家复用一个不可变String载荷，一次广播最多序列化一次，无支持玩家时不序列化。主/副服务器20tick调度、权威主世界时钟、版本序号、5秒新鲜度判断、失败处理及原版客户端能力门控保持不变。没有新增tick或实体/区块扫描。专项检查及全量构建不能替代实服MSPT测量。

> 当前实现基线：0.1.8。完整指令与权限以[离线 Wiki](../../documentation/wiki.html)和[指令表](../../documentation/commands.xlsx)为准；功能变更须同步代码、本文及统一文档源。

## 设计目标

运行时方案以服务端安全、跨服一致性和较低主线程开销为优先级。正常运行时数据库访问、迁移、统计落盘和归档在后台执行；停服停止游戏处理后，未落盘批次同步保存；游戏事件回调只完成必要校验、构造紧凑事件和内存聚合。

本文中的连接数、超时、队列容量和刷盘间隔是运维技术参数，不改变玩家玩法。它们可以按部署规模调整，但默认值必须保持保守。

| 单机嵌入式数据库 | H2 | 2.5.250 | 随模组 JAR 内嵌，无需安装服务 |
| MySQL 驱动 | MySQL Connector/J | 26.7.0 | 随模组 JAR 内嵌 |

群组服部署数据库使用 MySQL 8.4 LTS 的最新补丁版本，所有业务表使用 InnoDB。单人游戏和单服默认使用 H2 文件库，文件位于世界目录的 `contribution/contribution.mv.db`，数据库与业务表在首次启动时自动创建。建设度恢复日志也集中到同一世界目录的 `contribution/statistics-journal/`；启动时自动迁移旧的 `config/contribution/statistics-journal/`。若新旧两处同时存在，模组记录错误并停止初始化，游戏服务器本身仍可运行，两处原文件都会保留供管理员处理。运行配置仍在 `config/contribution/server.json`。停服后可以整体备份或恢复世界目录下的 `contribution/`；群组服 MySQL 数据必须另行备份数据库，不能只复制各子服的本地目录。H2 仅适用于单个服务器进程，不跨服共享。第三方依赖只从 Maven Central 获取并锁定版本；升级前需要重新执行编译、启动和数据库兼容测试。

短时去重使用有界 HashMap，每 20 tick 清理过期项，最多保留 50,000 个键。满载时新位置不增加行业建设度，原始操作统计独立处理；不引入额外缓存框架。

## 线程模型

每个服务器实例建立一个专用数据库执行器，默认两个工作线程和 1024 个有界排队位置。经济操作、查询、统计批次和迁移均进入该执行器，不允许在服务器主线程等待数据库结果。

建设度奖励使用主服每页 32 人的后台增量扫描，默认每 300 秒完成一轮；不在每次方块操作时直接计算贡献值。每日签到只在主线程每 20 tick 读取在线玩家 UUID 和现实秒数，先在内存聚合，默认每 60 秒提交一个后台数据库批次，正常关闭同步刷入。活动签到、商店下单和物品队列的 SQL 都通过同一个有界执行器；主线程只负责命令响应、可选客户端快照和最终物品交付。商店物品 ID 通过注册表直接查找，不逐帧扫描全部物品。

潜在高开销位置依次是：大量玩家跨服同时签到导致的数据库账户/签到行竞争；建设度奖励全服扫描与九行业乘权计算；股票每秒市场时钟更新与客户端快照发送；建设度高频事件的内存聚合及每 5 秒统计日志/数据库批次；大量商店物品交付时的背包插入。前两项已经批量或分页并移出主线程，统计事件只在主线程做轻量判定，所有任务受数据库线程数与队列容量限制。股票时钟仍按每秒推进，以维持 10:00—14:00 交易边界准确性；不声称该部分不产生数据库负载。实际服务器仍需用 MSPT 和数据库慢查询测量容量。

当队列已满时：

- 新的经济写入立即失败，并向玩家返回系统繁忙；
- 查询返回稍后重试；
- 高频统计继续在聚合器中合并，不为每个游戏事件创建独立数据库任务。

回调到游戏对象、发送反馈或访问世界状态时，必须重新调度到服务器主线程。数据库线程只能处理不可变请求、SQL 和纯数据结果。

## 连接池与事务

数据库启动只有一个在途任务；已可用时重复 start 不创建新连接池，STOPPED 是不可逆终态。关闭时先在短锁内发布终态，再在锁外等待执行器退出，避免启动线程等待同一锁。强制关闭移出的排队任务会完成为失败 Future，不留下永远 pending 的请求；每个任务捕获提交时的连接池，不读取可能被清空的字段。

每个服务器实例默认最多使用 4 个数据库连接，最少空闲连接为 1。默认连接等待超时为 3 秒，连接验证超时为 1 秒，连接最长存活时间为 25 分钟，保活间隔为 2 分钟。连接池不泄露数据库口令，也不在日志中打印完整 JDBC URL。

业务事务统一通过事务执行器管理：

1. 获取连接后关闭自动提交。
2. 设置合适的事务隔离级别并执行行锁、校验、更新和流水写入。
3. 成功时提交；任何异常时回滚。
4. 恢复连接状态并归还连接池。

账户写事务在群组服使用 MySQL 默认的 `REPEATABLE READ` 和显式 `SELECT ... FOR UPDATE`；单机 H2 使用同样的显式行锁与事务边界。只读查询不加账户行锁。事务体不得执行世界访问、网络等待或文件操作。

账户事务异常后在新事务中查询一次原幂等 ID；找到已完成流水则返回原结果，否则返回数据服务不可用，不盲目重复扣款。调用方后续重试必须沿用原请求。统计批次沿用原 ID 重试；数据库连接失效后每 600 tick 尝试重建连接池。确定性的参数、余额拒绝不自动重试。

## 数据库迁移

Flyway 对 MySQL 与 H2 分别加载对应方言的版本化迁移文件。单机 H2 在每次启动时执行迁移，首次连接同时创建数据库文件和业务表；群组服主服在 MySQL 账户具备建库权限时可创建 JDBC 地址指定的数据库并执行 `migrate`，其他子服启动时仅执行 `validate`，不创建数据库。迁移失败时，经济与统计服务保持不可用，服务器日志给出迁移版本和错误摘要，但不输出口令。

迁移不得修改已经发布的历史脚本。任何结构变化都通过新的递增版本脚本完成。破坏性迁移必须先备份，并在维护窗口由管理员显式执行。

## 统计缓冲与恢复

建设度和玩家统计先按紧凑复合键在内存中合并。默认每 5 秒或累计 500 个脏键时生成一个带全局唯一批次 ID 的批次，以先写本地恢复日志、再提交数据库的顺序处理。

内存最多保存 50,000 个聚合键，本地恢复日志最多占用 64 MiB。数据库不可用时继续合并已有键；达到内存上限后不再接收新的统计键并以限频日志告警，不能挤占服务器堆直至崩溃。恢复日志达到上限时停止采集新的建设度，既有代币账户仍按“数据库不可用即拒绝交易”的规则处理。

数据库确认批次提交后才能删除日志。正常关闭先最多等待 5 秒让日志线程退出，再保存未落盘批次，下次启动按原顺序、原 ID 重放。损坏、超过 64 MiB 或超过 50,000 个恢复键的日志会使统计暂停，原文件保留。异常断电仍可能丢失尚未刷盘的内存统计，正常运行的典型窗口最多约 5 秒；账户交易不依赖该缓冲。

已捕获的恢复批次在提交回调后继续处理下一批，不在每批之间额外等待 100 tick；始终最多一个日志写入或数据库提交在途。回调只处理既有批次，不立即捕获当天新缓冲，避免高频小事务。旧日关账使用按日期的安全屏障，每事务最多确认 32 日；行业按日逐步追赶，股票读取对应日期的行业快照。恢复不清空数据库、不改写已完成流水，也不重造采集暂停期间从未记录的玩家行为。缺少任何配置统计服务器的关账、哈希不符或历史快照缺失时保留等待保护。

## 配置与热重载

JAR 内置游戏事件映射只解析一次，发布为不可变对象；规则捕获逐项校验时复用同一份映射，避免在主线程按每个事件重复读取并解析整个 JSON。数据包的重载覆盖仍由 RuleSnapshot 单独读取并校验，缓存内置规则不冻结外部覆盖。

运行配置使用 UTF-8 JSON，默认路径为 `config/contribution/server.json`。`database.mode` 默认 `embedded`，无需另行设置；群组服必须显式设为 `mysql` 并填写共享 MySQL 地址和凭据。旧配置没有 `mode` 时，`enabled=true` 自动按 MySQL 读取，`enabled=false` 自动按嵌入式模式读取。数据库口令可以写入仅服务器可读的配置文件，也可以由环境变量 `CONTRIBUTION_DB_PASSWORD` 覆盖；日志和错误反馈不得回显口令。

数据库地址、凭据、服务器 ID、主服身份、统计服务器集合、线程数及连接池大小只在启动时读取，修改后需要重启。内置行业标签和已有事件映射通过主服 `/reload` 校验，下个游戏日 8 点切换；当前不实现自定义行业。

`rewards` 下的九行业发放权重、扫描间隔、现实日时区、签到秒数与周期奖励在启动时读取。商店商品仅首次从旧配置导入，此后以共享目录表为准。主服将这些配置的规范化 SHA-256 指纹写入共享数据库的 `reward_configuration`；每笔发放和购买核对指纹，不一致时拒绝操作。修改这些配置后应同步所有子服并重启，避免不同子服按不同奖励规则或周期运行；商品目录不纳入奖励配置指纹。

## 日志与审计

排行榜查询由独立 `LeaderboardService` 管理，只允许12个固定类别。每类别最多缓存100行，15秒共享缓存与在途Future，失败移除缓存，下次可重试；查询10秒超时，不在主线程等待。余额与历史收入排序使用新增V19索引，行业榜复用行业索引；总建设度由数据库聚合仍需扫描相关统计，不能宣称常数复杂度或未经实测的性能提升。服务端只按8行分页发送，排行榜不会按帧轮询数据库。

### 手动诊断与安全恢复

`/contribution diagnose` 限管理员（OP 2）与控制台使用，不要求客户端安装模组。每实例最多一个诊断会话，现实时间15秒冷却；数据库重连及报告查询异步执行，反馈回到服务器线程，每步最多等待10秒，不在主线程等待数据库。

报告包括数据库状态、服务器ID/主服角色、规则和统计缓冲状态、市场时钟日期/归属/新鲜度、行业及市场已核算日、缺失关账服务器与规则哈希、下一次股票结算所需行业快照。节点异常详细行最多16条，其余汇总，不回显数据库口令。

恢复请求重置正常任务的重试期限，触发已有统计提交、规则同步、时钟发布与核算调度；不清除在途标记，不另建并发结算，不强制抢占租约，不删除日志、伪造关账、补造历史快照或改写已完成流水。8:00—18:00核算窗口和交易保护保持生效。配置冲突、主世界日期回退、缺失节点和哈希不一致明确要求人工处理。

初次报告后100 tick（正常约5秒）再次查询并反馈复查结果，随后释放会话。游戏/空服暂停期间复查等待恢复运行。该命令检查后台数据与调度，不等同于客户端UI、网络链路或MSPT性能测试。

运行日志使用 SLF4J，并采用稳定的事件名和键值字段。普通成功事件不逐条写日志；批次汇总、状态切换和异常使用限频日志，避免玩家活动放大磁盘写入。

- `INFO`：启动版本、配置摘要、迁移结果、数据库状态切换、每日结算和统计批次汇总。
- `WARN`：重试、队列接近上限、恢复日志增长、非法配置和可降级故障。
- `ERROR`：迁移失败、数据一致性失败、恢复日志损坏和无法回滚的异常。
- `DEBUG`：开发环境中的请求路径和性能数据，默认关闭。

账户流水是权威审计记录；日志只记录流水 ID、幂等 ID、操作类型、来源、服务器 ID、耗时和结果状态。数据库口令、完整连接串、聊天备注和其他可能含敏感信息的文本不得进入普通日志。

每个实例每现实分钟最多输出一次 CONTRIBUTION_SERVER_STATE 与后台 CONTRIBUTION_DATABASE_STATE：主世界 tick、核算日、规则日期、缓冲/在途键、行业和市场已结算日、每台配置统计服务器已关日。缺少关账输出限频 INDUSTRY_WAITING_FOR_CLOSE；统计提交异常输出 STATISTICS_BATCH_FAILED 并保留日志。可选客户端按固定通道每分钟记录接收大小、股票日期、消息序号与新鲜度，解析异常保留堆栈；断线清理诊断限频状态。日志不包含完整载荷、口令或聊天备注。

## 频率限制与协议兼容

股票观察时钟使用独立的约 20 tick 心跳事务，单次最多一个在途；行业历史加载、每日结算等待及失败退避不控制心跳。数据库仍是主服归属和交易校验的权威，不接受客户端时钟。客户端按查询发起时的递增消息序号更新时钟，拒绝旧刷新结果覆盖较新推送；断线重置序号。股票专用屏幕不暂停集成服务器，真实暂停和连接失效仍保留 5 秒关闭交易保护。

查询和命令使用每位玩家独立的令牌桶，管理员批量查询另设全服上限。余额变更 API 主要受数据库队列、调用方身份和幂等约束保护，不在服务器主线程执行。命令/商店请求使用 RequestLimiter：每玩家容量 8，每 10 tick 恢复 1，全服每 tick 最多 40 次。贡献页面导航独立使用 250ms 间隔和单会话在途读限制，不将翻页误当成交易。玩家离服释放桶，停服清理桶及全服计数。

贡献、股票和商店都提供可选客户端快照与专用绘制界面，未安装客户端时使用 26.3 原生 Dialog，只有客户端声明对应 Fabric 接收能力时服务端才发送；否则打开原生 Dialog。原版客户端无需安装模组，文字命令始终保留。

## 归档与规则快照

生存服在游戏时间 8:00—18:00 每 600 tick 最多搬移 500 条过期流水，按 UTC 自然月归档到当前数据库的归档表；复制、删除处于同一事务，群组服归档表仍使用 InnoDB。原幂等记录永久保留，归档不重新计算余额。

规则 JSON 按 SHA-256 去重保存，核算日表只记录日期与哈希。`config_version=1` 表示当前规则结构版本，不是重载次数；实际规则身份由 `config_hash` 与核算日确定。每日结算正常从 8 点开始，失败重试和历史追赶仅在 8:00—18:00 执行。

## 事件计数热路径（0.1.14）

服务端完成事件只进行规则查询、资格检查与内存累加，不逐事件查询数据库、写恢复文件或发送网络包。相同核算日、主体、事件只保留一个计数器；距离与原始事件使用可变primitive long，避免每次增长重新装箱Long。只在100tick/500脏键刷批时生成独立Long快照，后台日志与SQL只读取快照，不共享可变计数器。容量上限、饱和运算、关账屏障与CSU5恢复格式不变。放置/挖掘和距离复用同一次调用的键；动作规则名称由枚举预生成，不在每次匹配时转换字符串。

事件入口平均O(1)，空间按不同日/主体/事件键数量增长，不按调用次数增长；标签匹配仍读取当前规则快照，不引入可能在/reload后失效的物品缓存。原版事件本身的执行成本、取结果的必要副本及每批持久化不是零成本。自动测试覆盖重复累加、批次隔离、清空、溢出及数据库恢复；未据此声称实服TPS或CPU提升百分比。

## 客户端兼容与本机部署

### 锻造升级组件保留（0.2.1）

强化名称和外观保留由原版SmithingTransformRecipe复制基底组件实现；61个配方不写item_name或item_model。工具与盔甲强化进度使用recipe_crafted及recipes注册表引用，不依赖inventory_changed。配方与进度由内置数据直接加载，无function。

原版result lore补丁会整体替换旧描述，因此SmithingUpgradeLoreMixin仅在SmithingTransformRecipe.assemble返回处合并单行「添翼」或「下界合金强化」标记，其他结果不处理。保留基底文字与样式，按标记文字去重，最多原版256行；已有256行且缺少新标记时保留原描述。范围为一次锻造结果的有界lore，不扫描背包、世界或tick；兼容原版客户端。原生CODEC、真实配方组装及独立服务端加载验证分别覆盖数据、逻辑及Mixin运行兼容，不能代替实际游戏内视觉测试。

### 周期调度与安全兜底（0.1.15）

签到通过入服、离服回调保留精确计时游标，周期在线名单采样降至每现实分钟，正常停服仍补计最后一段。跨午夜归属、不足一秒余量和时钟回退保护保留；每分钟采样也重新核对名单，避免遗漏离服回调使离线时间继续累加。

股票在线名单由服务器线程维护不可变快照，入服与离服使缓存失效，下一次读取刷新；每1200 tick重新核对一次以兜底。黑天鹅候选排除机器人，通知名单仍包含全部在线玩家，后台事务只使用捕获的独立快照。市场时钟20 tick心跳、5秒交易新鲜度校验、失败退避和数据库权威归属均不降低频率。

建设度奖励仍按配置间隔（默认300秒）分页核对全部玩家，包含离线与跨服玩家，每页最多32人。每页建设度读取从最多32次查询合并为一次有界IN查询；账户行锁、已发金额核对、逐玩家流水与同页事务不变。读取后的新增建设度在下一轮重新核对，不依赖可能丢失的内存脏名单。

统计关账和行业结算先检查已完成日期及退避条件，再检查未完成日期的统计缓冲。真正未完成的旧日屏障仍检查缓冲和在途批次，不提前确认关账。没有新增世界、区块或实体扫描，周期兜底只检查在线名单或数据库分页。测试覆盖名单失效与重核、批次快照隔离、跨日计时、离线奖励及重放；不将查询次数减少等同于未经实测的MSPT提升。

入服通过独立有界版本载荷通知可选客户端服务端的模组版本和 Minecraft 版本；客户端比较完整版本字符串，不一致时在聊天框提示双方版本和更新方向，不强制断线。原版客户端没有该接收器，不发送自定义载荷。能接收旧贡献 UI 但不能接收版本载荷的旧客户端，由服务端发普通聊天更新提示。旧服务端没有版本发布机制时不能保证比对，群组服应所有节点升级。版本检查只在入服执行，不新增 tick 查询。

当前项目的 run-gradle.ps1 build 成功后自动部署到用户指定的两个 mods 目录；精确匹配本模组文件名，先检查路径与锁，再暂存新 JAR，旧版本移到项目备份目录，最后校验安装文件 SHA-256。其他模组不动；文件被占用时停止部署并提示关闭游戏/服务端，不擅自杀进程。运行中不会热替换 Java 类，重启后生效。该脚本是本机工作流，不写入模组服务端运行逻辑，也不修改任意玩家客户端目录。

## 0.2.5 行业覆盖与退市返还

正常上市（ACTIVE）目标为20只，九行业各至少一只可买股票；待退市（RETIRING）不占正常上市名额，保留至14:00卖出窗口，列表可临时超过20只。补位优先缺失行业，必要时放宽最近五条退市记录的排除；不复用仍在市场的物品符号。候选被待退市股票占满时暂缓该行业最后一只正常股票退市，空位在14:00立即补齐。满额旧市场也检查覆盖，缩容不移除行业最后一只正常股票；主服启动后事务修复已有缺口。所有补位、缩容、退市返还及历史写入仍在市场行锁保护的同一事务中；失败回滚，启动修复成功后不重复运行。未完成退市按当日整数价格乘剩余股数全额返还，余额上限的未到账额留待领取，既有已完成返还不重算。不新增迁移。

## 0.2.6 股票专用候选映射

股票候选由开发者确认的专用XLSX导入，按物品命名空间ID与行业对应，不使用序号或行顺序。当前映射1535个物品，九行业分别为土建园林391、采矿冶金77、能源化工56、加工制造512、科技魔法86、农林牧渔133、军工食药102、流通服务62、文教民生116。

运行时从JAR内stock_industry_map.json加载“稳定行业ID→物品ID数组”，stock_item_names.json保存中文名，stock_catalog_manifest.json记录源表SHA-256和数量。首次使用一次加载、验证并缓存不可变行业列表；上市不读取XLSX、不逐次解析JSON。映射必须覆盖九个行业、每行业至少两个候选、ID存在于26.3注册表且全局唯一、中文名非空；异常会拒绝使用，不静默回退旧36候选。新上市股票采用新映射，已上市股票的行业、名称、持仓和历史记录保留，直到正常退市。

补位先在有合格候选的缺失行业中等概率选行业，再在该行业的合格物品中等概率抽取；若覆盖受最近退市排除阻挡，只对缺失行业放宽排除。行业覆盖齐全后，剩余名额先等概率选有候选的行业，再抽物品，候选数多不增加行业概率。ACTIVE与RETIRING的物品ID都排除，不重复上市。仍使用市场行锁及同一上市事务，无数据库迁移，不修改建设度标签和历史上市归属。
