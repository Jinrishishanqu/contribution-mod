# 跨服与数据一致性

> 当前实现基线：0.1.8。完整指令与权限以[离线 Wiki](../../documentation/wiki.html)和[指令表](../../documentation/commands.xlsx)为准；功能变更须同步代码、本文及统一文档源。

## 主服务器

群组服不设置大厅服。生存服是主服务器，并承担原本大厅服的作用。本文后续提到“主服务器”时，均指生存服。

群组服所有子服必须连接同一个 MySQL 数据库，账户表和流水表均使用 InnoDB 存储引擎。单人游戏与单服默认使用世界文件夹中的嵌入式 H2 数据库；它只供该服务器进程访问，不能作为群组服共享库，也不自动与 MySQL 同步。切换数据库模式不会自动迁移旧数据，必须先备份并另行迁移。

建设度与玩家统计只在 `statisticsServers` 配置列出的服务器采集，默认只包含生存服，也可以增加其他指定服务器。子服每 100 tick 同步主服发布的核算日与规则，切日先提交旧批次再确认关日，主服等待全部指定服务器确认后结算；未列入配置的子服不提交统计数据。无论配置多少个统计服务器，每日结算仍只由生存服执行。

## 原子事务与行锁

每次代币操作必须在同一个数据库事务中完成账户更新和流水写入。任意一步失败时，整个事务回滚。

修改账户前，使用以下查询对目标账户加行锁：

```sql
SELECT ... FOR UPDATE;
```

系统在持有行锁期间完成余额校验、账户更新和流水写入，并在事务结束后释放行锁。

## 流水 ID 与幂等 ID

每次操作均具有全局唯一的流水 ID 和幂等 ID。流水表分别为这两个字段建立唯一约束。

以下操作全部遵守幂等规则：

- 管理员命令；
- 签到；
- 建设度奖励和商店订单；
- 股票交易；
- 外部 API。

一次操作发生重试时，必须继续使用原幂等 ID，不能生成新 ID。

## 超时与重复请求

发生网络超时或返回结果丢失时，使用原幂等 ID 查询或重试：

| 状态 | 处理方式 |
| --- | --- |
| 幂等 ID 不存在 | 执行操作 |
| 操作已经完成 | 返回原操作结果，不重复修改账户 |
| 操作正在执行 | 当前异步调用等待事务结果；`IN_PROGRESS` 仅作为兼容状态保留，不主动返回 |
| 操作失败且事务已回滚 | 使用原幂等 ID 重新执行 |

幂等检查、账户更新和流水写入必须位于同一个事务中，避免多个子服同时提交相同操作。

## 全服级定时任务

- 全服级定时任务只在生存服运行。
- 其他子服不执行建设度日结算、股价更新和建设度奖励全服扫描，也不参与定时任务选主。现实日在线签到不属于全服核算任务：每台玩家所在服务器只累计本服玩家在线时间，汇总到共享数据库，由唯一日期键和事务阻止重复发奖。
- 所有基于游戏日的全服核算统一在主世界游戏时间早上 8 点执行。
- 生存服不使用分布式选主。
- 每个任务仍需记录任务日期、状态和唯一任务标识，防止生存服重启后重复执行。
- 任务记录同时保存尝试次数、更新时间、租约截止时间、完成时间和失败代码。生存服重启后只接管租约已经过期的 `RUNNING` 任务，并在同一记录上增加尝试次数，不能新建第二条同日同任务记录。

当前结算事务失败时整体回滚，保留 `RUNNING` 记录，等待 5 分钟租约过期后接管重试；`FAILED` 与 `failure_code` 字段为后续运维诊断保留。未收到全部子服关日确认时不创建结算任务。

## 数据库不可用

数据库不可用时，拒绝以下经济写入操作：

- 代币增减；
- 签到；
- 股票交易；
- 商城交易。
- 建设度奖励发放。

玩家会收到以下反馈：

```text
[贡献值] 数据服务暂时不可用，请稍后重试
```

数据库连接失效后每 600 tick 尝试重建；恢复后经济功能自动恢复，确认未执行的拒绝请求不会自动补录。若提交时连接中断，模组先用原幂等 ID 查询已提交流水；仍不能确认时，调用方必须使用原请求与幂等 ID 重试，不能直接认定未扣款。图形界面对嵌入式数据库与共享 MySQL 的不可用状态显示不同的排查提示。

## 建设度统计批次

0.1.13的V20新增event_activity_day和measurement_remainder。已完成原始数量、经济余量折算、个人/服务器建设度以及幂等批次标记同事务提交，回滚及重试不会丢余量或重复计分。CSU5恢复日志新增原始量区，仍读CSU2—4；无原始量的旧批次规范化哈希不变。旧日关账包含原始量缓冲及在途批次，不用今天的新活动阻塞旧日。原始量按核算日与事件聚合，不存每次触发历史或跨钩子序号。

玩家操作产生的高频统计先在执行该操作的服务器内存中聚合，再通过带全局唯一批次 ID 的批次写入当前数据库；群组服写入共享 MySQL。每个批次同时保存规范化内容的 SHA-256 `payload_hash`。批次重试必须继续使用原批次 ID 和原哈希；数据库以唯一约束保证同一批次只生效一次。同一批次 ID 携带不同哈希时必须拒绝处理并记录错误，不能把它当作成功重试。

同一个标准化建设度事件产生的当日服务器行业建设度增量和玩家行业建设度增量必须在同一数据库事务中写入。任意一方写入失败时，整个批次回滚，避免服务器统计与玩家统计不一致。玩家总放置数量和总挖掘数量可以包含在同一批次中。

行业总建设度仍由生存服在次日早上 8 点结算时，根据已完成核算日的当日服务器行业建设度统一累加，不能由各子服在玩家操作发生时直接修改。

统计批次与代币交易相互独立。数据库不可用时，代币交易必须拒绝；建设度统计进入有界内存缓冲并同步写入本地恢复日志。缓冲、刷盘和关闭策略见[运行时与性能架构](runtime-architecture.md)。

## 0.2.4 建设驱动股票迁移

V22保留历史股价、交易、持仓、建设度和原EMA，只修正当前繁荣度，为每日快照增加公式版本，增加行业幅度EMA。旧快照由股票追赶换算读取，原快照不重写。旧末名连续天数归零，已有退市和冷却日期保留。

黑天鹅保存第二玩家、规则版本、第二玩家基线和第二股票目标。升级前在途事件按旧规则完成，新事件用两人四行业规则。群组服统一升级，主服执行迁移。尺度、股价和事件应用同一事务，回滚及重试不重复吸收幅度、不重选目标。


## 0.2.5 行业覆盖与退市返还

正常上市（ACTIVE）目标为20只，九行业各至少一只可买股票；待退市（RETIRING）不占正常上市名额，保留至14:00卖出窗口，列表可临时超过20只。补位优先缺失行业，必要时放宽最近五条退市记录的排除；不复用仍在市场的物品符号。候选被待退市股票占满时暂缓该行业最后一只正常股票退市，空位在14:00立即补齐。满额旧市场也检查覆盖，缩容不移除行业最后一只正常股票；主服启动后事务修复已有缺口。所有补位、缩容、退市返还及历史写入仍在市场行锁保护的同一事务中；失败回滚，启动修复成功后不重复运行。未完成退市按当日整数价格乘剩余股数全额返还，余额上限的未到账额留待领取，既有已完成返还不重算。不新增迁移。

## 0.2.6 股票专用候选映射

股票候选由开发者确认的专用XLSX导入，按物品命名空间ID与行业对应，不使用序号或行顺序。当前映射1535个物品，九行业分别为土建园林391、采矿冶金77、能源化工56、加工制造512、科技魔法86、农林牧渔133、军工食药102、流通服务62、文教民生116。

运行时从JAR内stock_industry_map.json加载“稳定行业ID→物品ID数组”，stock_item_names.json保存中文名，stock_catalog_manifest.json记录源表SHA-256和数量。首次使用一次加载、验证并缓存不可变行业列表；上市不读取XLSX、不逐次解析JSON。映射必须覆盖九个行业、每行业至少两个候选、ID存在于26.3注册表且全局唯一、中文名非空；异常会拒绝使用，不静默回退旧36候选。新上市股票采用新映射，已上市股票的行业、名称、持仓和历史记录保留，直到正常退市。

补位先在有合格候选的缺失行业中等概率选行业，再在该行业的合格物品中等概率抽取；若覆盖受最近退市排除阻挡，只对缺失行业放宽排除。行业覆盖齐全后，剩余名额先等概率选有候选的行业，再抽物品，候选数多不增加行业概率。ACTIVE与RETIRING的物品ID都排除，不重复上市。仍使用市场行锁及同一上市事务，无数据库迁移，不修改建设度标签和历史上市归属。
