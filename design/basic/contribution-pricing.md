# 贡献点边际计价规格：放置与挖掘（发放侧分段）

> 状态：**设计规格，未实现**。`x`、`y`、`z` 为预设值，**最终数值由设计者拍板**（见 §14）。
> 对齐基线：0.2.6。本规格**只重设"贡献点价格"**，不改动建设度获取、繁荣度、EMA 与股票。
> 配套的数值对比与逐例演算见[贡献点计价前后对比（注释版）](contribution-pricing-comparison.md)。

---

## 0. 目标与边界

**目标**：限制单位时间内贡献点的发行速度，使**批量建造（含打印机）的单日收益最多只比手搭玩家高 20%**。

**边界**——本规格明确不改动的东西：

| 不改动 | 说明 |
| --- | --- |
| 建设度获取 | 放置 / 挖掘仍是每方块 1 点建设度，九行业归账、20 tick 去重、创造模式排除全部照旧 |
| 繁荣度 / EMA / 股票 | 完全不受影响。打印党依旧会抬高建设度与繁荣度，这是本方案已知且**接受**的代价，不在本规格职责范围内 |
| 玩家统计界面 | 显示的建设度、放置 / 挖掘次数不变 |
| 其他来源的贡献点 | 合成、交通、钓鱼、交易、繁殖、机器产出等仍按原权重线性发放，公式不变 |

**唯一改动**：放置与挖掘这一类来源，由"每点建设度固定乘权重"改为**按当日累计建设度分段递减单价**。

### 为什么放在"发放侧"，而不是"建设度侧"

早期设想是把分段直接作用在建设度上（例如第三档"每 480 块计 1 点"）。放弃的原因是：

1. 建设度是 `BIGINT` **非负整数列**，而第三档单价 `z ≈ 0.002` 是小数量级，整数化会把它抹平为 0；
2. 建设度同时喂给 EMA 与繁荣度，改动它会波及其它系统（不属于本规格职责）；
3. 放在发放侧后，`x / y / z` 可以是**任意小数**，小数部分由"应发池"天然滚存——正好满足原规格 §9 的精度要求。

## 1. 与现有发放机制的对齐

**现有实现（0.2.6）**：主服务器每 300 秒扫描一次，按个人九行业**累计**建设度 `D_i` 计算应发总量，只发差额。设 `P` 为该玩家已从建设度领取过的总额：

$$
E=\left\lfloor\sum_{i=1}^{9} w_iD_i\right\rfloor,\qquad G=\max(0,\;E-P)
$$

**新实现**：把 `E` 拆成"其他来源"与"放置 / 挖掘"两部分，前者保持原公式，后者改用分段函数。

设：

- `D_i^{other}`：行业 `i` 中**非放置 / 挖掘**来源的累计建设度；
- `n_d`：第 `d` 个核算日内、该玩家放置 + 挖掘产生的**建设度合计**（九行业求和）；
- `F(n_d)`：该日的放置 / 挖掘应得贡献点（分段函数，见 §3），可为小数；
- `PMC = Σ_d F(n_d)`：放置 / 挖掘应得贡献点**累计池**（定点保存，跨日、重启、跨服保留）；
- `EffW = Σ_i w_i · D_i^{other}`：其他来源的加权建设度（小数保留，永不丢弃）。

则：

$$
E=\left\lfloor EffW + PMC\right\rfloor,\qquad G=\max(0,\;E-P)
$$

**对齐要点**：

1. 扫描周期、主服独占、每页 32 人、`G>0` 才发、同事务更新余额 / 总收入 / `DEVELOP` 流水 / `P`、上限截断——**全部沿用现状，不改动**。
2. 权重 `w_i` 对放置 / 挖掘**不再生效**（改由 `F` 计价）；对其他来源**照旧生效**。
3. 小数不再"存在建设度里"，而是存在 `EffW` 与 `PMC` 两个池里；两者都以 `DECIMAL(30,8)` 定点保存并终身滚存、绝不倒扣。

## 2. 输入参数

| 符号 | 含义 | 来源 |
| --- | --- | --- |
| `x` | 第一档单价，单位 **贡献点 / 建设度**（放置 / 挖掘 1 方块 = 1 建设度，故等价于"贡献点 / 方块"） | **保留为符号，由设计者最终定值** |
| `a` | 手搭玩家日均放置 + 挖掘建设度，即第一档上界 | 实测统计（当前预设 `1000`，合并挖掘后建议重测） |
| `b` | 第二档上界 | 由设计倍数 `k` 决定：`b = k·a` |
| `c` | 硬顶上界，超过不再计收益 | 可配置（当前预设 `50000`） |
| `p` | 第二档折扣因子 | 设计取值（推荐 `0.1`） |
| `n` | **单个玩家、单个核算日**内放置 + 挖掘的建设度合计 | 运行时统计 |

待求量：第二档单价 `y`、第三档单价 `z`。

> 注释：`n` 的统计口径是"去重后的成功放置 / 挖掘建设度"，与创造模式排除、20 tick 去重完全一致，因此打印机无法通过快速补墙拆墙把 `n` 刷到更高档位。

---

## 3. 分段计价函数

**累计形式**（`(t)^+ = max(t,0)`）：

$$
F(n)=a\cdot x+y\cdot\big(\min(n,b)-a\big)^+ + z\cdot\big(\min(n,c)-b\big)^+
$$

**边际形式**（第 `n` 块方块的单价，更直观）：

$$
m(n)=
\begin{cases}
x, & 0<n\le a\\
y=p\cdot x, & a<n\le b\\
z, & b<n\le c\\
0, & n>c
\end{cases}
$$

| 当日放置 + 挖掘建设度 `n` | 累计收益 | 该档边际单价 |
| --- | --- | --- |
| `0 < n ≤ a` | `n·x` | `x` |
| `a < n ≤ b` | `a·x + (n−a)·y` | `y` |
| `b < n ≤ c` | `a·x + (b−a)·y + (n−b)·z` | `z` |
| `n > c` | `F_max`（封顶不再增长） | `0` |

收益上限（填满分段，等价于 `n → ∞`）：

$$
F_{max}=a\cdot x+(b-a)\cdot y+(c-b)\cdot z
$$

---

## 4. 目标约束

手搭玩家的日收益为 `F(a) = a·x`；要求极限收益为其 1.2 倍：

$$
F_{max}=1.2\cdot a\cdot x
$$

等价于溢出预算恒等式：

$$
(b-a)\cdot y+(c-b)\cdot z=0.2\cdot a\cdot x
$$

---

## 5. 求解通式

给定 `y = p·x` 与 `b`，唯一确定 `z`：

$$
y=p\cdot x,\qquad z=x\cdot\frac{0.2\,a-(b-a)\,p}{\,c-b\,}
$$

---

## 6. 合法性约束

启动与热重载时必须校验，违反则整份配置无效（沿用 `RewardConfigGuard` 的"拒绝整份配置"策略）：

1. 单价递减：`0 ≤ z < y < x`；
2. 区间递增：`a < b < c`（`a`、`b`、`c` 为正整数）；
3. 第二档不得吃掉全部溢出：`(b-a)·p ≤ 0.2·a`；
4. 附加：`x > 0`，`0 ≤ p < 1`。

由 (1)(2) 可推出 `p` 的下界：

$$
p>\frac{0.2\,a}{c-a}
$$

---

## 7. 推荐默认形状与预设数值

取 `k = 2`（即 `b = 2a`）、`p = 0.1`（第二档打一折）：

$$
y=0.1\,x,\qquad z=x\cdot\frac{0.1\,a}{c-2a}
$$

该组合成立的前提（由 `z < y` 推出）：`a < c/3`（当 `c = 50000` 时即 `a < 16666`）。

**预设实例**：`a = 1000`、`b = 2000`、`c = 50000`、`p = 0.1`。

按目标"每游戏日最多 720 贡献点（1.2 倍）、平均 600 贡献点（1 倍）"反解第一档单价：

$$
x=\frac{600}{a}=\frac{600}{1000}=\mathbf{0.6}\ \text{贡献点/建设度}
$$

于是：

| 区间（当日放置 + 挖掘建设度） | 边际单价 | 该档满额贡献 |
| --- | --- | --- |
| `0 – 1000` | `x = 0.6` | `600` |
| `1000 – 2000` | `y = 0.06` | `60` |
| `2000 – 50000` | `z = 0.00125` | `60` |
| `> 50000` | `0` | — |

上限验算：

$$
F_{max}=600+60+60=720=1.2\times600\quad\checkmark
$$

> **价格最终由设计者拍板。** `x = 0.6` 只是为满足"手搭 600 / 封顶 720 每游戏日"的**预设值**。
> `x` 具有缩放不变性（见 §11）：改变 `x` 只线性缩放绝对数值，`y / z` 与段位结构、1.2 倍结论均不变。
>
> ⚠ **量级提示**：现网每方块的建设度权重是 `0.004`（1/250），即手搭 1000 块/日约得 `4` 贡献点；
> 若采用预设 `x = 0.6`，手搭玩家变为 `600` 贡献点/日，绝对量级放大约 **150 倍**。
> 采用该预设时，**商店价格、签到奖励、活动奖励、股票初始价等所有贡献点数值必须按同一倍数重新校准**，否则经济将严重通胀。

## 8. 前后价格对比

完整的倍数表、绝对数值表与逐例演算见[贡献点计价前后对比（注释版）](contribution-pricing-comparison.md)。摘要：

| 日放置 + 挖掘建设度 `n` | 旧：线性 `0.004·n` | 旧倍数 | 新：`F(n)` | 新倍数 |
| --- | --- | --- | --- | --- |
| 1000（手搭基准） | 4 | 1.00× | 600 | 1.00× |
| 2000 | 8 | 2.00× | 660 | 1.10× |
| 5000 | 20 | 5.00× | 663.75 | 1.106× |
| 10000 | 40 | 10.00× | 670 | 1.117× |
| 50000 | 200 | 50.00× | 720 | 1.20× |
| 100000 | 400 | 100.00× | 720 | 1.20× |

结论：旧规则下打印收益随方块的**线性**增长（可达手搭的 100 倍以上）；新规则把倍数**硬性压在 1.2 倍以内**。

## 9. 结算流程（对齐现有核算日）

1. **建设度照旧**：放置 / 挖掘命中标签后，按现有批次写入 `player_industry_stats`、`industry_day_accumulator`、`player_activity_stats`；同时在批次事务内累加当日的放置 / 挖掘**建设度**计数（`player_daily_place_mine`）。
2. **核算日关账**：主服到达新核算日（主世界时间 `8:00` 边界，同现有公式）后，对每个在建玩家逐日计算 `F(n_d)`，**幂等**写入该日记录的 `credit` 字段，并累加进玩家的 `PMC`。
   - 唯一键 `(player_uuid, stat_date)` 保证重复启动不重算；未在线的玩家由结算任务补算。
3. **周期发放**：主服每 300 秒扫描（现状不变），按 `E = ⌊EffW + PMC⌋`、`G = max(0, E − P)` 发放差额。
4. **事务**：`PMC`、余额、历史总收入、`DEVELOP` 流水、`P` 在同一事务提交；达到 `Integer.MAX_VALUE` 上限时只发可装下部分，剩余留在 `PMC`。

> 注释：关日与发放是**两个独立环节**。关日把"当日创造的建设度"折算成"应得贡献点"存进池子；发放只是把池子里的整数部分付出去。因此即使某天扫描失败，池子里的钱不会丢。

## 10. 数据、配置与迁移改动

**数据库（新增迁移，版本号接在现有之后）**

| 对象 | 变更 | 用途 |
| --- | --- | --- |
| `player_industry_stats` | 增加列 `place_mine_development BIGINT NOT NULL DEFAULT 0` | 分离出各行业的放置 / 挖掘建设度，`D_i^{other} = development − place_mine_development` |
| `player_daily_place_mine` | 新表：`(player_uuid, stat_date, development BIGINT, credit DECIMAL(30,8) NULL)`，唯一键 `(player_uuid, stat_date)` | 当日放置 / 挖掘建设度与已结算应得贡献点；`credit IS NULL` 表示当日尚未结算 |
| `player_development_reward` | 增加列 `place_mine_credit DECIMAL(30,8) NOT NULL DEFAULT 0` | 放置 / 挖掘应得贡献点累计池 `PMC` |

**配置（`config/contribution/server.json` 的 `rewards`）**

```jsonc
"placeMinePricing": {
  "enabled": false,     // 默认 false = 保持现网线性权重，便于平滑迁移
  "a": 1000,            // 第一档上界（手搭日均建设度），正整数
  "b": 2000,            // 第二档上界，正整数，须 a < b < c
  "c": 50000,           // 硬顶上界，正整数
  "p": "0.1",           // 第二档折扣因子，0 ≤ p < 1
  "x": "0.6"            // 第一档单价（贡献点/建设度），> 0；最终由设计者拍板
}
```

- `y = p·x`、`z = x·[0.2a − (b−a)p]/(c−b)` 由系统推导，**不单独配置**，避免三者不一致。
- 校验 §6 全部约束，违反则拒绝整份 `rewards` 配置并保留旧配置（现有行为）。
- `placeMinePricing` 整体纳入 `rewards` **配置指纹**，群组服自动保持一致。

**迁移行为（重要）**

- 升级时老玩家的 `place_mine_development` 默认为 `0`，于是历史放置 / 挖掘建设度仍按旧权重线性计发，`PMC` 从 `0` 起算。
- 即"**老账照旧、新账新规**"：不追补、不倒扣、不重算历史。这是平滑迁移，需在版本说明中明示。
- 若设计者希望历史放置 / 挖掘也按新规则，需要单独的一次性重算任务，属于本规格之外的可选项。

## 11. 数值精度与缩放不变性

- `z` 相对 `x` 极小（预设实例约 `0.002083x`）。`EffW`、`PMC`、`credit` 全部为 `DECIMAL(30,8)`，中间计算用 `BigDecimal`（8 位小数四舍五入），**不得用整数截断**，否则第三档会被抹平为 0。
- **缩放不变性**：整套定价对 `x` 线性齐次。`x` 取任意值，最优的 `y`、`z` 同比例缩放，段位结构与"打印最多只比手搭多赚 20%"的结论均不变。`x` 仅决定绝对数值量级。

## 12. 自测验证点

实现后必须全部通过（沿用原规格 §8，并把 `F` 的口径改为"当日折算后的贡献点"）：

- `F(a) = a·x`
- `F(b) = a·x + (b−a)·y`
- `F(c) = 1.2·a·x`
- 对任意 `n > c`，`F(n) = 1.2·a·x`（超出部分不再增收益）
- 单调性：`n₁ < n₂ ⇒ F(n₁) ≤ F(n₂)`
- 边界：`F(0) = 0`；`n` 恰为 `a / b / c` 时档位归属正确
- 配置校验：违反 §6 任一约束时整份配置被拒
- `EffW` 与 `PMC` 小数跨日 / 重启 / 跨服保留；`G` 在 `PMC` 增长后正确补发
- 关日结算幂等：重复触发同一核算日不重复累加 `PMC`
- 迁移：`placeMinePricing.enabled = false` 时行为与 0.2.6 完全一致
- 断言：任意 `n` 下 `F(n) ≤ 1.2·a·x`

## 14. 待设计者拍板项

1. **`x` 最终取值**——决定绝对量级。预设 `0.6`（对应手搭 600 / 封顶 720 每游戏日）。
2. **`a` 是否重测**——合并"放置 + 挖掘"后，手搭玩家的日均建设度会高于纯放置统计，建议重新采样后再定 `a`。
3. **`k` 与 `p`**——当前推荐 `k = 2`、`p = 0.1`，即第二档打一折、区间到两倍。
4. **是否对九个行业设差异化系数**——当前设计为**全行业统一边际单价**（多产业综合计价）；若需要行业差异，可对 `m(n)` 再乘一个默认 `1.0` 的行业系数 `r_i`。
5. **是否把其他来源也纳入分段**——当前只折放置 / 挖掘（它们才有打印漏洞）；其余来源线性不变。
6. **存量数值校准倍数**——若确认 `x = 0.6`，全服贡献点数值需要一个统一的重新标定倍数。
