# 玩家统计数据

## 系统定位

玩家统计数据是基本功能，用于长期记录玩家参与服务器游玩和建设的情况。系统在数据模型和累计语义上模仿原版统计数据，但由服务端模组独立持久化，不直接修改原版统计文件。

独立实现的原因如下：

- 群组服行业数据需要通过 MySQL 共享；单服保存在世界内嵌入式数据库中，当前只实现九个内置行业；
- 原版客户端不包含自定义统计项的名称和界面文本；
- 统计需要与服务器行业建设度共享去重、行业匹配和批量写入结果；
- 原版统计值使用 32 位整数，不适合服务器长期累计建设度。

原版客户端通过 `/contribution` 打开原生 Dialog 统计页面，也可通过文字命令查询；无需安装客户端模组。

## 统计项目

每名玩家至少维护以下统计项目：

| 统计 ID | 含义 | 计数单位 |
| --- | --- | --- |
| `contribution:total_blocks_placed` | 玩家累计成功完成的方块放置操作次数 | 成功放置操作 |
| `contribution:total_blocks_mined` | 玩家累计成功完成的方块挖掘操作次数 | 成功挖掘操作 |
| `contribution:industry_development/<行业路径>` | 玩家在指定行业的累计建设度 | 通过行业规则计算的建设度 |

行业统计使用稳定的行业 ID，当前页面显示九个内置行业；不提供行业删除或自定义行业切换。

所有统计值使用非负 64 位整数，取值范围为 $0$ 至 $2^{63}-1$。数据库使用带非负检查约束的有符号 `BIGINT`，与 Java `long` 的范围保持一致。执行加法前必须检查溢出；理论上达到上限后保持最大值并记录错误日志，不能因为统计溢出而取消玩家已经成功完成的游戏行为。

## 总放置数量

玩家总放置数量只统计由玩家直接发起并由服务端确认成功的方块放置。

- 客户端动画、取消事件、放置失败和仅消耗物品但没有产生方块的行为不计数。
- 按玩家成功完成的操作次数计数。门、床等一次生成多个方块位置的操作仍只累计 1 次。
- 自动化机器、命令、世界生成、活塞移动、流体扩散和其他环境变化不计入玩家总放置数量。
- 统计不要求方块属于某个行业的 `place_<行业路径>.json` 标签。
- 同一位置一秒内的重复操作仍计入总放置数量；短期去重只影响服务器和玩家行业建设度。

## 总挖掘数量

玩家总挖掘数量只统计由玩家直接发起并由服务端确认成功的方块破坏。

- 按玩家成功完成的操作次数计数。一次挖掘连带移除多个方块位置时仍只累计 1 次，不按方块位置数或掉落物数量计数。
- 创造模式直接破坏仍属于玩家成功挖掘，计入总挖掘数量；行业规则可以单独排除创造模式建设度。
- 爆炸、机器、命令、活塞和环境变化造成的方块移除不计入玩家总挖掘数量。
- 统计不要求方块属于某个行业的 `mine_<行业路径>.json` 标签。
- 同一位置一秒内的重复操作仍计入总挖掘数量；短期去重只影响服务器和玩家行业建设度。

## 玩家行业建设度

玩家行业建设度表示某名玩家通过有效建设行为为各行业贡献的累计建设度，不进行每日重置。

玩家合成、放置和挖掘分别通过 `craft_<行业路径>.json`、`place_<行业路径>.json` 和 `mine_<行业路径>.json` 匹配行业。每次事件遵守游戏模式、唯一行业归属和来源计量规则。行业建设度不设置每日上限。

只有 `statisticsServers` 配置列出的服务器采集玩家统计。默认只在生存服统计，也可以显式增加其他指定服务器；群组服所有统计服务器连接同一个 MySQL 数据库，因此同一玩家在不同统计服务器产生的数据汇总到同一账户。单服模式使用世界内嵌入式数据库。玩家行业建设度只接受生存模式或冒险模式下产生的玩家行为。

方块放置和挖掘必须先通过服务器建设度设计中的 20 tick 同位置去重。通过去重后，同一个标准化建设度事件同时增加：

- 对应行业的当日服务器建设度；
- 当前玩家在该行业的累计建设度。

行业总建设度不在玩家操作发生时直接修改，而是在次日早上 8 点结算时由已完成核算日的当日建设度统一累加。

被去重的操作不会增加上述任何建设度。玩家合成没有方块坐标，不适用该去重机制。

自动化、机器、环境和其他没有明确玩家主体的来源只增加服务器行业建设度，不增加任何玩家的行业建设度。未来如果某类自动化行为需要归属玩家，必须在该来源设计中明确所有者解析和防刷规则，不能根据最近在线玩家推测所有者。

## 事件处理顺序

玩家直接放置或挖掘方块时，按以下顺序处理：

1. 服务端确认操作已经成功。
2. 按本次成功操作增加 1 次玩家总放置或总挖掘统计。
3. 使用玩家操作标签匹配行业规则。
4. 执行统计服务器、游戏模式和唯一行业归属校验；当前不增加额外维度、工具条件。
5. 使用子服、维度、玩家、操作类型、坐标和方块 ID 执行 20 tick 去重；方块 ID 不包含方块状态。
6. 通过去重后，生成一个标准化建设度事件。
7. 服务器行业聚合器和玩家行业聚合器消费同一个事件。

原始操作统计与行业建设度统计相互独立。某个方块没有行业归属或建设度被去重，不会撤销已经确认的总放置或总挖掘统计。

## 查询

原版客户端使用以下命令查询：

```text
/contribution stats
/contribution stats <玩家>
```

- 所有玩家可以查询自己的统计数据。
- 管理员可以通过玩家名称或 UUID 查询在线或离线玩家。
- `<玩家>` 使用目标选择器时必须恰好选中一名玩家。
- 默认输出总放置数量、总挖掘数量以及当前启用行业的累计建设度。
- 原版客户端可直接打开图形界面，也可使用聊天文本查询。

## 持久化

当前数据库至少保存以下数据：

| 数据表 | 主键 | 主要字段 |
| --- | --- | --- |
| 玩家活动统计 | 玩家 UUID | 玩家名称、名称小写规范值、总放置数量、总挖掘数量、更新时间 |
| 玩家行业建设度 | 玩家 UUID、行业 ID | 累计建设度、更新时间 |

高频统计先在子服内存中聚合，再通过带唯一批次 ID 的批次写入数据库。同一批次中的服务器行业增量与玩家行业增量应在同一个数据库事务中写入；任意一方失败时整个批次回滚。

网络超时后必须使用原批次 ID 重试。数据库不可用期间可以继续保留有界的内存统计缓冲，但不得无限增长；缓冲上限、落盘恢复和服务器关闭时的处理方式见[运行时与性能架构](../infrastructure/runtime-architecture.md)。
